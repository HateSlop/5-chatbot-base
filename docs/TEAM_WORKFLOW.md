# 팀 협업과 실행 환경

화면·API·자료의 경계를 함께 정하고, 기능이 이어지는지 자주 확인하세요. 아래 내용은 팀의 실행 환경을 맞추기 위한 예시입니다.

## 먼저 합의할 것

- 사용자가 실제로 하게 될 핵심 행동과 캐릭터 경험
- 꼭 보여줄 기능, 시간이 남으면 추가할 기능, 실패했을 때의 화면
- 프런트와 서버의 경계: 같은 앱인지, 다른 앱인지, 요청·응답 형식은 무엇인지
- 자료를 쓰는 경우 원본의 출처와 검색이 필요한 질문
- 팀이 공통으로 사용할 실행 방법과 공개 배포 계획

화면 시안과 예시 API 응답을 함께 보면 화면에 필요한 데이터와 서버가 반환할 데이터를 맞추기 쉽습니다. 구현 난이도, 자료의 출처, 배포 제약도 이때 확인하세요.

## Docker를 협업에 쓰는 방법

Docker Compose는 **같은 Python 버전과 의존성, 실행 명령**을 공유하는 데 유용합니다. 특히 한 팀원에게만 생기는 설치 문제를 재현할 때 도움이 됩니다. 이 저장소의 Compose 파일은 개발용 Flask 서버와 읽기 전용 코드 마운트를 제공합니다. 호스트에서 파일을 수정하고 컨테이너에서 같은 코드를 실행합니다. [Docker Compose 개요](https://docs.docker.com/compose/intro/features-uses/)

```bash
docker compose up --build
docker compose ps
docker compose logs -f chatbot
docker compose exec chatbot python -m unittest discover -s tests -v
docker compose down
```

새 패키지를 추가한다면 `requirements.txt`를 함께 수정하고, 다른 팀원은 `docker compose up --build`로 이미지를 다시 만듭니다. 오류를 공유할 때는 **실행 명령, 기대한 결과, 실제 결과, 관련 로그의 비밀 값을 지운 부분**을 전달하세요. Compose는 개발 환경을 맞추는 도구이며, 실제 서비스는 팀이 선택한 다른 구성으로 배포할 수 있습니다.

Conda/venv도 충분한 개발 경로입니다. 기존 수업 경험을 활용해 빠르게 개발하고 싶다면 그것을 쓰세요. Docker와 Conda를 한 실행 경로에 중첩할 필요는 없습니다. 프로젝트의 `requirements.txt`와 Python 버전, 팀 README의 실행 명령을 맞추면 됩니다. [Conda 환경 관리](https://docs.conda.io/projects/conda/en/stable/user-guide/tasks/manage-environments.html)

**권장 실습:** 개인 작업은 익숙한 Conda로 진행하더라도, 팀 통합 시점에 한 번은 Compose로 앱을 빌드·실행하고 `ps`·`logs`·`exec`으로 상태와 테스트를 확인해 보세요. 팀원이 서로 다른 OS에서 같은 절차를 따라 본 경험이 배포 전 문제를 찾는 데 도움이 됩니다. 이것은 학습을 위한 권장이며 Docker 사용 여부 자체를 결과물의 점수로 삼자는 뜻은 아닙니다.

## 변경을 합치는 짧은 주기

1. 작은 기능 단위로 작업하고, 화면과 API가 만나는 지점을 일찍 연결합니다.
2. 변경 설명에는 무엇을 바꿨는지, 어떻게 실행·확인했는지, 남은 문제가 무엇인지 적습니다.
3. 서로의 변경을 검토할 때 기획 의도와 사용 흐름도 함께 확인합니다. 코드만 통과해도 사용자 경험이 어긋날 수 있습니다.
4. 배포 후 공개 URL에서 실제 사용자처럼 사용하고 오류·응답 속도·자료 정확성을 점검합니다.

Git 브랜치와 PR은 팀이 익숙한 방식으로 운영하세요. 테스트는 지금 제공된 스모크 테스트를 출발점으로 삼되, 팀이 새로 만든 핵심 기능의 성공·실패 사례를 직접 확인해야 합니다.
