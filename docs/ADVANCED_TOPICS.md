# 자료 검색과 확장 기능

## 검색이 답변을 개선하는지 먼저 확인

캐릭터의 말투, 성격, 금기처럼 짧고 변하지 않는 규칙은 설정이나 프롬프트에 둘 수 있습니다. 수십 개의 사건·인물 관계·작품 설정처럼 질문마다 필요한 사실이 달라지면 검색을 고려하세요. 검색이 실제로 필요한 질문 5~10개를 먼저 준비하고, 검색 전후의 답변을 비교하면 구현 방향을 잡기 쉽습니다.

## 최소 RAG 흐름

1. **자료 준비:** 팀이 사용할 권한이 있는 자료를 모으고, 제목·출처·갱신일을 기록합니다.
2. **분할과 인덱싱:** 읽기 좋은 단위로 나누고 검색에 필요한 표현을 만듭니다. 벡터 검색을 선택했다면 임베딩 모델과 차원 수를 기록하세요.
3. **검색:** 질문에 맞는 자료를 찾아 관련성이 낮은 결과를 제외합니다. 검색 결과가 없을 때의 응답도 정합니다.
4. **답변:** 캐릭터 설정과 검색 결과를 함께 써서 답변을 생성합니다. 자료에 없는 사실을 아는 척하지 않도록 지시하고 결과를 확인합니다.
5. **검색 결과 점검:** 개발 중 `sources`로 어떤 자료가 검색됐는지 확인합니다. 이 값은 답변의 실제 인용 목록이 아니며, 기본 채팅 화면에는 표시하지 않습니다.
6. **평가:** 질문, 기대 근거, 검색 결과, 답변, 실패 이유를 표로 남깁니다. 검색 실패와 생성 실패를 구분합니다.

ChromaDB를 쓴다면 작은 로컬 실험은 `PersistentClient`로 시작할 수 있습니다. 운영 배포의 저장 위치는 배포 플랫폼에 맞춰 다시 결정하세요. 임베딩 모델이나 분할 방식이 바뀌면 인덱스를 다시 만들고 평가해야 합니다. [Chroma Python 클라이언트](https://docs.trychroma.com/reference/python)

## 모델 호출

기본 실행은 모델 API를 호출하지 않습니다. 먼저 화면과 데모 응답을 확인한 뒤, 실제 답변을 연결할 때 `services/generator.py`의 데모 생성을 교체합니다. 기본 예시는 운영진이 제공하는 OpenAI API 키를 사용하며, 설정 방법은 [모델 연결 가이드](MODEL_SETUP.md)를 참고하세요. OpenAI 외 공급자는 팀에서 선택할 수 있는 대안입니다. 이 경우 필요한 키와 사용 조건을 팀이 확인하고, 키는 로컬 환경 변수로 관리하세요. 모델 이름과 설정은 코드 여러 곳에 적지 말고 환경 변수로 관리합니다.

### 개발 초기 API 비용 줄이기

1. 먼저 **키 없이 데모 답변**으로 화면과 서버의 요청·응답을 확인합니다.
2. 실제 모델을 연결한 뒤에는 대표 질문 몇 개만 보내 말투와 설정이 반영되는지 확인합니다. OpenAI API 키는 운영진이 제공하며 사용량에는 한도가 있을 수 있습니다. 로컬에서는 `.env`에 보관하고 Git에 올리지 마세요. 다른 공급자를 선택했다면 키 제공 여부와 비용·사용 조건을 먼저 확인하세요.
3. 답변 길이와 자동 재시도 횟수를 제한하고, API 사용량을 기록합니다. 같은 질문으로 답변 품질과 응답 시간을 비교하고 운영진이 안내한 사용 범위 안에서 테스트하세요.

처음부터 많은 질문을 반복하거나 긴 대화 기록을 계속 보내지 않아도 됩니다. 연결과 프롬프트를 확인한 다음, 품질을 판단하는 데 필요한 질문만 추가하세요.

API 실패·시간 초과·요금 제한의 사용자 표시와 재시도 정책을 정하세요. 외부 서비스 호출은 비용이 발생할 수 있으므로 테스트 과정에서 불필요한 반복 호출을 피하세요.

## 이미지와 메모리

`image`는 브라우저에서 접근 가능한 이미지 URL입니다. 답변별 이미지는 처음부터 복잡한 감정 분석을 만들기보다, **어떤 상황에 어떤 이미지를 보여줄지** 몇 가지 규칙으로 정해 시험하는 것이 좋습니다. 예를 들어 인사에는 인사 장면을, 특정 장소가 대화에 등장하면 그 장소 이미지를 연결하고, 맞는 장면이 없으면 이미지를 보내지 않습니다.

이미지 선택은 감정·상황 라벨에 따른 경로 선택, 이미지별 장면 설명과 답변의 텍스트 임베딩 비교, 이미지·텍스트 모델을 이용한 이미지 자체의 임베딩 비교 중에서 고를 수 있습니다. 라벨 방식은 명확한 몇 가지 상태에 간단하고, 설명문 방식은 설명에 담긴 맥락을 비교하며, 이미지 임베딩은 이미지 내용을 직접 반영합니다. 과제에서 임베딩 유사도를 요구한다면 라벨 선택만으로 끝내지 말고 요구 기준에 맞는 임베딩 방식을 구현하세요. 팀이 고른 이미지와 직접 작성한 테스트 답변으로 선택·생략이 적절한지 확인합니다. 자세한 내용은 [대화용 이미지 안내](../data/images/README.md)를 보세요.

이미지 사용 권한과 공개 URL을 확인하고, 프로필 이미지를 고정해서 보여주는 기능과 답변에 맞는 이미지를 선택하는 기능을 구분하세요.

현재 브라우저는 이전 메시지를 화면에 보여주지만 서버 요청에는 **현재 메시지와 이름만** 보냅니다. 여러 턴을 기억하게 하려면 메시지 목록 또는 세션 ID를 API 계약에 추가하고, 보관 범위와 삭제 방법을 설계해야 합니다. 사용자별 데이터가 섞이지 않게 확인하세요.

## 검증 질문 예시

- 자료에 명시된 사건을 물었을 때 맞는 문서를 찾고 답하는가?
- 자료에 없는 사건을 물으면 모른다고 말하는가?
- 비슷한 이름의 두 캐릭터를 혼동하지 않는가?
- 이전 대화 정보가 필요한 질문을 메모리 구현 전후에 어떻게 다르게 처리하는가?
- 검색에 실패하거나 모델 API가 멈췄을 때 사용자가 이해할 수 있는 메시지가 나오는가?

정확도 수치는 표본과 판정 방법을 함께 적으세요. 단순히 “RAG 적용”이라고만 쓰지 말고 어떤 실패가 줄었는지 보여주세요.
