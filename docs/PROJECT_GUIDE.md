# 프로젝트 가이드

## 목적

성격·말투·세계관이 대화 중에도 유지되는 캐릭터 챗봇을 만듭니다. 이 베이스 코드의 데모 응답은 완성된 챗봇이 아닙니다. 화면·라우트·프레임워크는 기획에 맞게 바꿀 수 있습니다. 과제의 세부 제출 내용과 일정은 [5기 합동과제 공지](https://app.notion.com/p/3f30a64dbab780439c34c03187d0feb3)를 확인하세요.

## 결과 기준

1. 사용자가 접근할 수 있는 **공개 URL**과 핵심 기능 시연 경로를 제공합니다. 배포 플랫폼은 자유입니다.
2. LLM 답변에서 캐릭터의 성격·말투·세계관을 유지하고, 빈 질문과 외부 API 실패를 다룹니다.
3. 대화에 맞는 이미지를 답변에 함께 보여줍니다. 먼저 몇 가지 상황별 이미지 규칙으로 출력·생략 기준을 시험하고, 최종 결과에서는 답변 문장과 이미지의 임베딩 유사도를 비교해 선택합니다. 실제 이미지와 답변 문장을 직접 비교하려면 둘을 같은 벡터 공간에 놓을 수 있는 이미지·텍스트 임베딩 모델이 필요합니다. 프로필 이미지를 고정해서 보여주는 것만으로는 이 항목을 충족하지 않습니다.
4. JavaScript/HTML/TypeScript 등을 사용해 메시지 전송과 응답 표시가 실제로 작동하는 채팅 화면을 만듭니다. 제공된 화면을 그대로 사용할 필요는 없습니다.
5. 자료를 쓰는 기획이라면 원본 자료의 출처와 검색·답변 반영 과정을 설명하고, 실제 질문으로 확인합니다.
6. 팀이 선택한 구조와 기술의 이유, 알려진 한계, 재현 가능한 실행 방법을 README에 기록합니다. API 키·개인정보·저작권이 확인되지 않은 자료는 공개 저장소에 넣지 않습니다.

기본 화면의 수나 디자인, Flask 사용, 단일 캐릭터, Docker 사용 여부는 결과 기준이 아닙니다. 기획에 따라 여러 캐릭터, 독립 프런트엔드, 다른 서버 언어·프레임워크, 음성이나 새로운 인터랙션을 설계할 수 있습니다. 구현한 기능을 공개 URL에서 안정적으로 보여주고 팀의 선택을 설명할 수 있어야 합니다.

제출 형식·마감은 위 공지가 최종 기준입니다. 이 문서는 베이스 코드의 구현 가이드입니다.

## RAG를 언제 쓰나요?

RAG는 먼저 관련 자료를 찾고 그 내용을 모델의 답변 맥락에 넣는 방식입니다. 캐릭터 설정이 짧고 모든 답변이 창작 대화인 경우에는 검색이 오히려 불필요할 수 있습니다. 반대로 세계관 문서, 캐릭터의 과거 사건, 작품별 설정, 학교·동아리 정보처럼 **질문에 따라 찾아야 할 사실**이 있다면 RAG가 적합합니다.

이 프로젝트에서는 자료 검색을 활용한 답변을 **기본 권장 경로**로 둡니다. ChromaDB는 수업에서 다룬 구현 예시입니다. 키워드 검색, 다른 벡터 저장소, 관리형 검색도 가능합니다. RAG가 맞지 않는 팀은 검색을 형식적으로 끼워 넣는 대신 다음을 제시하세요.

- 캐릭터 경험에 검색이 필요하지 않은 이유
- 수업에서 배운 내용을 활용하는 다른 기술 요소와 그 구현 결과
- 해당 선택이 효과적이었는지 확인할 질문·실험·지표

예를 들어 자료가 풍부한 세계관 챗봇은 출처를 포함한 답변을 평가하고, 즉흥 상황극 챗봇은 일관성·대화 상태 관리·안전한 실패 처리를 평가할 수 있습니다. 단순한 SDK 호출이나 프롬프트 한 줄만으로 기술 적용을 설명하기는 어렵습니다.

## 필수 이미지 출력과 선택 확장

- **답변별 이미지 출력:** 먼저 이미지 후보와 장면을 정리하고, 상황별 규칙으로 어떤 답변에 어떤 이미지를 보여줄지 시험합니다. 최종적으로는 이미지 내용과 답변 문장을 비교할 수 있는 임베딩 모델을 연결해 유사도가 높은 후보를 선택합니다. 텍스트 임베딩 모델로 이미지 설명문을 검색하는 방식은 초기 실험에 쓸 수 있지만, 이미지 자체의 임베딩과 비교하는 방식과 다릅니다. ChromaDB는 벡터를 저장하고 가까운 후보를 검색하는 선택 도구이며, 임베딩은 모델이 만듭니다. 충분히 가까운 후보가 없으면 이미지를 생략합니다. 구현 자리는 `services/image_selector.py`, 화면에 전달하는 필드는 `image`입니다.
- **대화 메모리:** 이전 턴 또는 이전 방문의 정보를 보관해 뒤의 답변에 반영합니다. 화면에 이전 메시지가 남아 있는 것만으로는 서버가 그 내용을 알고 있는 것은 아닙니다. 저장 기간, 사용자 구분, 삭제 방법을 설계하세요.
- **음성·스트리밍·로그인:** 기획상 도움이 될 때 추가합니다. 기능 수보다 실제 동작과 검증이 중요합니다.
